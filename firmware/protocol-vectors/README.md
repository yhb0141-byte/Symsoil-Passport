# 硬件协议一致性向量

`confirmation-v1.json` 是固定的合成测试材料，包含贡献入账、积分兑换、原话许可和精确有限授权四种内容。`delivery-result-v1.json` 是社区服务对最终接受/拒绝结果签名的合成向量，它把原成员回复签名、请求编号、传输号和结果编号绑定在同一个 canonical 帧中。两份文件只保存合成正文、公钥、canonical内容与P1363签名；没有私钥、成员访问凭证、真实授权或真实交易。

移植固件时分别核对：

1. 完整内容 canonical 字节是否一致，SHA-256 是否等于请求摘要。
2. 所有帧字段是否精确一致，包括社区、成员、版本、设备、挑战和计数器。
3. P-256/SHA-256 签名是否按64字节 `r || s` 解释，而非直接按 DER 解释。
4. 修改语义、金额、内容摘要或计数器后，原签名是否拒绝。
5. 对象键使用 UTF-16代码单元排序；正文按UTF-8编码，不进行额外的 Unicode 规范化。
6. 最终结果的服务签名绑定原成员签名、请求和传输号；修改接受/拒绝、传输号或成员签名后必须拒绝。

Node检查：

```sh
npm run test:protocol
```

独立Python检查（仅开发工具使用第三方密码学库）：

```sh
python -m pip install cryptography
python scripts/verify-protocol.py
```

Python实现独立构造JSON与签名帧，并转换P1363到该库的DER接口；既核验正向签名，也核验确认计数器和交付结果关键字段修改后失败。额外序列化用例包含中文、emoji、控制字符、UTF-16与码点顺序不同的键、孤立代理字符及数组顺序。Node检查还拒绝非安全整数、浮点、缺项数组和其他非JSON值。

这些检查证明协议实现兼容，不证明真实设备持有人、可信显示、按键、私钥保护、BLE安全、服务身份或离线撤销。向量里的签名不能用于实际社区服务；部署时还需要受控配置、轮换和停用社区服务公钥。

维护者需要生成一套新合成材料时可运行 `node scripts/generate-protocol-vectors.mjs`；该命令会替换文件里的合成公钥和签名，不应作为普通启动或CI步骤。不会保存生成过程中使用的私钥。

## 服务信任配置向量

`trust-v1.json` 包含四组公开的 `symsoil-trust/1` 根签名配置：首次启用、换钥、停用和恢复，以及同一业务结果在旧/新服务钥匙下的签名。没有私钥。`npm test` 核验Node编码和签名；`npm run test:firmware-host` 用生成的公开头文件逐字节核对C编码，并链接OpenSSL 3验证真实P-256及交付生命周期；`python3 scripts/verify-protocol.py` 独立重建二进制帧并核验根签名。

信任配置的CRC不是签名，配置镜像的严格一致性也不等于防完整Flash回滚。协议格式和本地交接边界见 [固件信任配置](../../docs/firmware-trust.md)。
